# Chips vs. G-Memory: Multi-Agent Memory Design

## Executive answer

Chips and G-Memory both use three levels, but their three levels solve different representation problems.

- **G-Memory's three tiers** organize accumulated multi-agent experience across abstraction levels: interactions, queries, and insights.
- **A Chip's three layers** organize the knowledge extracted from one paper inside every semantic pin:
  - **L1 — Structure:** containment and hierarchy.
  - **L2 — Mechanism:** typed binary relations between entities.
  - **L3 — Events:** reified multi-party events that preserve conditions, roles, evidence, and outcomes.

Therefore, G-Memory and Chips are not interchangeable representations. G-Memory provides a runtime memory lifecycle, whereas a Chip provides a richer, source-grounded representation of a paper. A Chip-based system can address G-Memory's multi-agent problem, but it needs a retrieval and runtime-use mechanism around the paper Chips. The original paper evidence must remain separate from experience generated by agents.

The strongest research direction is not to copy G-Memory's hierarchy. It is to use the existing Chip layers for **role-conditioned, mechanism-aware, and evidence-grounded memory retrieval**, then test whether this reduces irrelevant retrieval, unsupported claims, and negative transfer in multi-agent systems.

## 1. What one Chip represents

One paper Chip is a structured, source-grounded representation of one paper. Its stable semantic pins capture the paper's main content, such as:

1. `problem_gap`
2. `method_mechanism`
3. `evaluation_validation`
4. `result_outcome`
5. `grounding_implementation`
6. `reuse_transfer`

Some current research-paper Chips separate `experimental_setting` and `implementation`, producing seven practical pins. This is a schema variant, not an additional architectural layer.

Every pin can contain the following three layers.

### L1: Structure

L1 states what components exist and how they are contained or decomposed.

Example:

```text
MultiAgentMethod
├── PlannerAgent
├── CriticAgent
├── ExecutorAgent
└── SharedMemory
```

L1 is useful for broad navigation, component discovery, and low-cost retrieval.

### L2: Mechanism

L2 states how two entities are related. Existing relation families include relations such as `feeds`, `causes`, `implements`, `replaces`, `mitigates`, `adds_cost`, `constrains`, and `tests`.

Multi-agent extensions could include:

```text
PlannerAgent  DELEGATES_TO  ExecutorAgent
CriticAgent   CRITIQUES     ProposedPlan
SharedMemory  FEEDS         PlannerAgent
RepairStep    MITIGATES     CoordinationFailure
```

L2 is useful when the system must retrieve a causal or operational mechanism rather than merely a related paper.

### L3: Events

L3 reifies an event involving several entities and preserves its context. Existing Chip event families include `GapBinding`, `Forward`, `Training`, `EvalPipeline`, `Result`, `Compatibility`, and `Grounding`.

A multi-agent extension could add events such as:

```yaml
event_type: CollaborationEpisode
roles:
  proposer: PlannerAgent
  critic: CriticAgent
  executor: ExecutorAgent
inputs:
  - Task
  - RetrievedEvidence
conditions:
  communication_budget: 4_rounds
outcome:
  status: success
evidence:
  - paper_section_4_2
```

Unlike a collection of pairwise edges, this event preserves who did what, under which conditions, using which evidence, and with what result.

The formal specification of these layers is included in [`EXTENDED_CHIP_SCHEMA_REFERENCE.md`](docs/EXTENDED_CHIP_SCHEMA_REFERENCE.md).

## 2. What G-Memory represents

G-Memory is a runtime memory system for multi-agent systems. It organizes the experience accumulated while agents solve tasks into three tiers:

1. **Interaction Graph:** messages and information flow among agents for a particular problem-solving trajectory.
2. **Query Graph:** tasks, task outcomes, and relationships between current and past queries.
3. **Insight Graph:** higher-level lessons distilled from multiple task trajectories.

Its memory process includes storing new trajectories, connecting related queries, distilling or updating insights, retrieving relevant past experience, and projecting selected memory to the agents that need it.

References:

- [G-Memory NeurIPS 2025 paper](https://papers.neurips.cc/paper_files/paper/2025/file/136a45cd9b841bf785625709a19c6508-Paper-Conference.pdf)
- [Official G-Memory implementation](https://github.com/bingreeky/GMemory)
- [G-Memory arXiv record](https://arxiv.org/abs/2506.07398)

## 3. The exact architectural difference

| Dimension | G-Memory | Chips |
|---|---|---|
| Primary object | Multi-agent runtime experience | Knowledge extracted from one paper |
| Main purpose | Learn from previous task-solving trajectories | Preserve reusable, traceable scientific knowledge |
| Three levels mean | Increasing abstraction across episodes | Increasing relational expressiveness within each pin |
| Lowest level | Agent messages and their information flow | Component hierarchy and containment |
| Middle level | Queries and relationships between queries | Typed binary mechanisms |
| Highest level | Insights distilled across queries | Context-rich multi-party events |
| Ground truth | Observed agent trajectory and task status | Claims and evidence from the source paper |
| Retrieval unit | Past interactions, related queries, and insights | Pins, structures, relations, events, and evidence anchors |
| Update behavior | Continually adds and summarizes runtime experience | Should preserve the paper's extracted claims as immutable evidence |
| Main strength | Operational multi-agent memory lifecycle | Typed, mechanistic, source-grounded knowledge |
| Main risk | Noisy or incorrect experiences can become influential memories | Static Chips alone do not learn from new executions |

The key point is:

> G-Memory's three tiers answer **at what abstraction level is an experience stored?** A Chip's L1/L2/L3 answer **how richly is a paper claim represented?**

## 4. How the two organizations can be combined

Each kind of G-Memory object can be represented using all three Chip layers. This creates a two-dimensional design rather than forcing one three-level system into the other.

| Runtime scope | Chip L1: structure | Chip L2: mechanism | Chip L3: event |
|---|---|---|---|
| Interaction | Agents, messages, tools, artifacts | sends, critiques, delegates, repairs | collaboration episode or handoff |
| Query | Tasks, subtasks, constraints | similar-to, depends-on, transfers-to | task attempt and outcome |
| Insight | Lessons, reusable primitives, failure modes | supported-by, contradicts, generalizes-to | transfer claim or compatibility result |

For example, a paper describing a debate-based multi-agent method can be encoded as follows:

- L1 records the debater, judge, rounds, shared evidence, and answer objects.
- L2 records which agent critiques which proposal and which evidence supports the final decision.
- L3 records the complete debate episode, including roles, number of rounds, stopping rule, task conditions, and measured result.

This is more expressive than storing the paper as a flat passage or a single summary.

## 5. Can Chips solve the same problem as G-Memory?

### What Chips can already do

Paper Chips can provide multi-agent systems with:

- grounded descriptions of agent architectures;
- reusable coordination mechanisms;
- task and model compatibility conditions;
- successful and failed experimental findings;
- implementation anchors;
- explicit evidence for retrieved claims;
- transfer hypotheses that can be checked before use.

### What static paper Chips cannot do alone

A collection of immutable paper Chips does not, by itself:

- observe a new agent conversation;
- remember which retrieved mechanism worked on a new task;
- relate the current query to previous execution attempts;
- distill new lessons from multiple runtime trajectories;
- revise retrieval priorities using runtime outcomes.

Therefore, claiming that static Chips completely replace G-Memory would be too strong. To solve the exact same continual multi-agent memory problem, the system needs a runtime-use layer around the Chips. That runtime layer must not overwrite paper-derived facts.

## 6. Proposed method: a Chip-based multi-agent memory engine

The proposed system keeps one Chip per paper and adds an operational engine around the Chip collection.

### 6.1 Immutable paper-Chip store

The original Chip remains tied to its paper. Every retrieved claim retains:

- the source paper;
- pin and layer identity;
- evidence anchor;
- extraction or verification status;
- applicable conditions and limitations.

### 6.2 Layer-aware retrieval

Retrieval should reflect the information need:

- **L1 retrieval** finds relevant architectures and components quickly.
- **L2 retrieval** finds mechanisms, dependencies, costs, constraints, and failure repairs.
- **L3 retrieval** finds complete procedures or results whose roles and conditions match the current task.

A staged retrieval process could be:

```text
task query
  -> retrieve candidate Chips and L1 substructures
  -> expand only relevant L2 mechanisms
  -> retrieve matching L3 events and evidence
  -> verify compatibility and contradictions
  -> project a small subgraph to each agent role
```

This should be tested against whole-document retrieval, flat chunk retrieval, and G-Memory retrieval.

### 6.3 Role-conditioned projection

Different agents should receive different views of the same grounded Chip subgraph.

```text
project(chips, task, agent_role, token_budget)
    -> grounded role-specific subgraph
```

Examples:

- A planner receives task decomposition, dependencies, and compatibility constraints.
- A critic receives assumptions, limitations, contradictory evidence, and failure cases.
- An executor receives implementation steps, interfaces, and resource requirements.
- A verifier receives evaluation protocols, baselines, metrics, and evidence anchors.

This prevents every agent from receiving the same large context and makes the memory useful to the agent's actual responsibility.

### 6.4 Compatibility and negative-evidence gate

Before a method is transferred from a paper to a new problem, the engine should test:

- task-type compatibility;
- model and tool assumptions;
- data availability;
- communication and compute budget;
- evaluation objective;
- known failure conditions;
- contradictory results in other Chips.

The system should be able to return **do not transfer** or **insufficient evidence**, not only a recommended method. This is a likely advantage over similarity-only memory retrieval.

### 6.5 Separate paper truth from runtime observations

Runtime observations must never silently become paper facts. A safe lifecycle is:

```text
paper-derived claim
    -> immutable and source-grounded

runtime observation
    -> candidate record
    -> repeated validation
    -> promoted runtime insight
    -> still labeled as runtime-derived
```

The runtime record may cite the Chip mechanism it used, but it should live in an append-only usage record or a separately typed experience Chip. This preserves provenance and prevents a failed agent trajectory from corrupting the representation of the original paper.

### 6.6 Cross-Chip reasoning

For the same problem, the engine can compare mechanisms from several papers. For a different problem, it can search for transferable primitives rather than retrieve papers only by topic similarity.

Useful cross-Chip relations include:

- `supports`
- `contradicts`
- `extends`
- `replaces`
- `same_assumption_as`
- `compatible_with`
- `incompatible_with`
- `tested_under`
- `fails_under`
- `transfers_to`

These relations must retain their source and confidence. A cross-paper inference should be clearly distinguished from a claim directly made by either paper.

## 7. How Chips could perform better on G-Memory's problem

The following are research hypotheses, not established results.

### 7.1 Better mechanism retrieval

Embedding similarity may retrieve an episode that sounds relevant but uses an incompatible mechanism. L2 retrieval can explicitly select a causal or operational relation, while L3 retrieval checks its conditions and outcome.

**Hypothesis:** mechanism- and condition-aware retrieval reduces irrelevant experience reuse and negative transfer.

### 7.2 Better grounding

An agent can trace a recommendation back to the exact paper, pin, event, and evidence anchor.

**Hypothesis:** grounded projections reduce unsupported claims and make multi-agent decisions easier to audit.

### 7.3 Better representation of multi-party coordination

A multi-agent episode is not naturally reducible to independent pairwise edges. An L3 event can preserve multiple agents, tools, artifacts, conditions, and outcomes together.

**Hypothesis:** event-level retrieval improves role assignment, handoffs, and repair after coordination failures.

### 7.4 Better handling of failures and contradictions

Chips can explicitly encode failure conditions, limitations, added costs, incompatible assumptions, and conflicting evidence.

**Hypothesis:** a negative-evidence gate reduces the propagation of bad strategies through the agent team.

### 7.5 Lower context cost through projection

The engine can retrieve a small connected subgraph instead of sending a full paper, full Chip, or complete past trajectory to every agent.

**Hypothesis:** role-specific subgraphs maintain or improve task success with fewer context tokens.

## 8. Different problems that Chips can address

Because L1/L2/L3 are representation layers rather than domain-specific tiers, the same architecture can support problems beyond runtime multi-agent memory.

### Research comparison and synthesis

- L1 aligns method components across papers.
- L2 compares mechanisms and assumptions.
- L3 compares experimental events under matched conditions.

### Research-gap verification

- connect a claimed gap to existing methods;
- retrieve counterexamples and negative evidence;
- distinguish an untested combination from a genuinely missing capability.

### Experiment design

- retrieve compatible evaluation pipelines;
- preserve dataset, model, budget, metric, and baseline roles in L3 events;
- flag mismatched comparisons before experiments are run.

### Reproduction and implementation

- map paper components to repositories, files, interfaces, and configurations;
- trace an observed reproduction failure to an assumption or missing dependency;
- keep implementation advice linked to paper evidence.

### Scientific multi-agent teams

- planner retrieves gap and mechanism structures;
- method agent retrieves reusable procedures;
- experiment agent retrieves evaluation events;
- critic retrieves limitations and contradictions;
- verifier checks every proposed claim against evidence.

### Cross-domain method transfer

The engine can match a reusable mechanism to a new domain through typed function, constraint, and compatibility relations instead of relying only on topical similarity.

## 9. Recommended multi-agent Chip extensions

The core pin architecture and L1/L2/L3 semantics should remain stable. Multi-agent support can be added through a small controlled vocabulary.

### L1 node types

- `AgentRole`
- `Team`
- `Message`
- `Task`
- `Subtask`
- `Tool`
- `Artifact`
- `MemoryState`
- `Insight`
- `Outcome`

### L2 relation types

- `SENDS_TO`
- `DELEGATES_TO`
- `CRITIQUES`
- `REVISES`
- `VERIFIES`
- `REPAIRS`
- `CONSULTS`
- `SHARES_WITH`
- `BLOCKS`
- `SUPPORTS`
- `CONTRADICTS`
- `GENERALIZES_TO`

### L3 event types

- `CollaborationEpisode`
- `Delegation`
- `Handoff`
- `Debate`
- `Consensus`
- `ToolUse`
- `MemoryRead`
- `MemoryWrite`
- `FailureRepair`
- `TaskOutcome`
- `PrimitiveTransferClaim`

These additions extend the ontology without replacing the existing three-layer model.

## 10. Experimental plan

The comparison must separate the benefit of structured Chips from the benefit of the runtime engine.

### Systems

1. No long-term memory.
2. Flat paper-chunk RAG.
3. Whole-Chip retrieval.
4. Chip L1 retrieval.
5. Chip L1 + L2 retrieval.
6. Chip L1 + L2 + L3 retrieval.
7. Full Chip retrieval with role-conditioned projection.
8. Full Chip retrieval with projection and compatibility/negative-evidence gate.
9. G-Memory.
10. Hybrid G-Memory runtime experience plus grounded paper-Chip retrieval.

### Tasks

Use both same-domain and transfer settings:

- repeated tasks from one benchmark;
- tasks with similar wording but different constraints;
- tasks requiring transfer across domains;
- adversarial cases where a superficially similar method is incompatible;
- tasks for which the source literature contains a known negative result.

### Metrics

- task success;
- retrieval precision;
- role relevance of retrieved memory;
- unsupported-claim rate;
- negative-transfer rate;
- contradiction detection;
- repair success after failure;
- context-token and latency cost;
- memory contamination rate;
- source traceability;
- calibration when evidence is insufficient.

### Essential ablations

- remove L2 mechanisms;
- remove L3 events;
- remove evidence anchors;
- remove negative findings;
- remove compatibility checks;
- use one identical projection for all agent roles;
- replace connected-subgraph retrieval with embedding-only top-k retrieval;
- allow runtime observations to mix with source claims, to measure contamination risk.

## 11. Primary research claim to test

A defensible central hypothesis is:

> In multi-agent problem solving, role-conditioned retrieval over grounded L1/L2/L3 paper Chips will reduce unsupported memory use and negative transfer relative to flat retrieval, while preserving or improving task success. Adding separately labeled runtime experience will provide continual adaptation without contaminating source-grounded paper knowledge.

This claim is stronger and more specific than saying that Chips are generally better than G-Memory. It identifies the expected advantage, its cause, the baseline, and the failure modes that the evaluation must measure.

## 12. Recommended first prototype

The smallest meaningful prototype should:

1. keep each existing paper Chip immutable;
2. add the multi-agent node, relation, and event vocabulary;
3. build separate L1, L2, and L3 retrieval indexes;
4. implement role-conditioned connected-subgraph projection;
5. add compatibility and negative-evidence checks;
6. store execution feedback separately from paper claims;
7. evaluate against flat RAG, whole-Chip retrieval, and G-Memory.

This prototype preserves the defining Chip architecture while making it operational for the same class of multi-agent memory problems and for broader scientific reasoning tasks.
